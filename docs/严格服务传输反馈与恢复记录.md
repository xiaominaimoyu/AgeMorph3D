# K3传输反馈与手动恢复

日期：2026-10-29。本批完成[剩余关键工作计划](剩余关键工作开发计划.md)K3中可独立推进的客户端传输子项。两份现有模型清单仍登记`unresolved`，严格加载均拒绝；没有修改清单、许可状态或模型资格。完整G0/G1/G2及人工质量、长时设备验收继续未完成。

## 改动及边界

[协议](transport-recovery-v1.json)在验证前写入；[客户端](../frontend/src/services.ts)增加：

- 无应用错误详情的HTTP 503显示固定的暂时不可用/可能繁忙提示及手动重试建议，不回显原始响应体，不断言一定过载。已有`MODEL_NOT_READY`等JSON详情继续保留。
- 跨源失败时浏览器可能不暴露状态码。提示检查后端、地址和跨域设置，并建议关闭其他连接后手动重试；不虚构可读取的HTTP 503。
- WebSocket关闭码1009提示大小限制，1013提示暂时不可用；其他关闭保持通用说明，不回显不可信reason。原错误终结、代际隔离、定时器/待帧清理及手动重连保持。
- 编码后发送前拒绝空Blob、非JPEG类型及超过2 MiB的帧；恰为2 MiB可发送。拒绝时停止当前检测，后续需要显式连接，不自动重开摄像头或重连。

原128 KiB逐chunk响应预算、30秒HTTP与8秒实时截止时间、`no-store`、重定向拒绝、单飞/镜像及序号语义保持。没有改后端启动参数、HTTP/WS路由或推理实现。

## 首轮失败与收口

[第一轮](../output/research/transport-recovery-20261029/browser-v1/report.json)两浏览器各12项完成，但整体失败于结束检查：脚本尝试重新bind端口，被Windows返回`EADDRINUSE`。随后[系统监听/PID独立观察](../output/research/transport-recovery-20261029/cleanup-native-v1.json)显示无监听、原PID已退出；因此不能将bind拒绝直接解释为服务未关闭，也没有据此证明唯一底层原因。

只修测试脚本的检查方式：启动前及结束后使用Windows监听表，结束后同时核对自有子进程退出。未改客户端、后端、测试案例或期望；两轮17来源中仅harness一个指纹变化，原失败和冻结记录保留。第二轮通过。Windows测试子进程以SIGTERM结束，记录的是进程退出/端口释放，不用它证明带模型的优雅关闭或长时资源验收。

最终文件/链接收口脚本首轮以Windows默认GBK读取UTF-8测试日志失败，改为显式UTF-8后复核；没有修改应用、测试结果或验收条件。

```powershell
& 'D:/JAVA run tools/node.exe' --experimental-transform-types --test frontend/tests/services.test.ts
& 'D:/JAVA run tools/node.exe' frontend/tests/transport-recovery-browser.mjs `
  --output-dir output/research/transport-recovery-repro-v1
```

[显式浏览器harness](../frontend/tests/transport-recovery-browser.mjs)只允许新的`output/`目录，记录启动PID、真实/合成范围、原始网络失败、来源指纹与结束状态；存在其他监听会拒绝启动，不终止用户现有进程。服务器仅绑定loopback，退出清理仅作用于本次创建的进程和连接。
