## 1. 目标与实施顺序

延续项目顺序：**前端 → 后端 → 获取训练集 → 数据集预处理 → 训练**。后端阶段先完成服务与真实静态重建，再接实时姿态和已有模型能够支持的年龄功能。预训练权重属于后端推理依赖；训练数据的批量获取、预处理和训练仍在后续阶段。

后端阶段不能把尚未训练的年龄方向作为已有能力。若没有来源明确、适配当前拓扑且经过验证的预训练年龄资产，则交付真实重建、实时姿态及年龄模块接入接口，将年龄效果验收保留到训练阶段。无能力时明确禁用相关操作。

验收分四个出口，分别记录，不能互相替代：

| 出口 | 可以宣布完成的条件 | 不能由此推断 |
|---|---|---|
| G0：服务契约 | 无权重也能启动；状态准确；输入、错误、资产和 WS 契约测试通过 | 检测、重建或年龄模型已就绪 |
| G1：真实静态重建 | 实际照片经检测、重建产生对应 GLB；前端查看、导出、错误恢复可用 | 已具有年龄变换能力或完整后脑几何 |
| G2：真实实时姿态 | 实体摄像头帧经真实算法得到框、关键点、姿态；单飞和资源释放通过 | 每帧重建表情、几何，或达到 30 FPS 推理 |
| G3：年龄能力 | 有可追溯的年龄形状/纹理模型，分别通过形变、UV、连续性与身份保持检查 | 能预测个人未来真实容貌 |

## 2. 当前代码决定的接口边界

以 [api.md](api.md)、[contracts.ts](../frontend/src/contracts.ts)、[services.ts](../frontend/src/services.ts)、[main.ts](../frontend/src/main.ts) 和 [viewer.ts](../frontend/src/viewer.ts) 为依据。

| 当前事实 | 后端实现和联调要求 |
|---|---|
| 健康面板只显示 `models` 键名，不消费 ready/mode 值 | 增加明确的模型状态和能力协议，同时修改前端状态、按钮；仅扩展后端 JSON 不足以完成联调 |
| GLB 加载器要求有效的 `age_20/45/70` 三个目标 | 普通重建须新增明确的静态资产模式；保留现有完整年龄资产校验，禁止用三份零位移伪装年龄能力 |
| `shape/expr/shape_aged` 只校验和保存，不重建网格 | 身份形状和表情必须已应用到返回网格；年龄滑块几何来自 GLB 内 morph |
| “生成年龄纹理”操作要求 `/api/aging` 返回 `texture_url` | 只有真实纹理模型可用才开放此操作；只有 `shape_aged` 的响应不能使该操作成功 |
| HTTP 重建姿态没有应用；WS 只应用绝对旋转 `R` | 优先返回正面 canonical 网格；算法姿态需转换到同一坐标系，防止网格烘焙姿态后再次旋转 |
| 网格居中且最大边归一化为 2.8，`t` 只保存为元数据 | 平移、真实相机内参和尺度标定另设后续任务，不把毫米平移直接施加到视口 |
| 纹理覆盖作用于可支持材质，未定义多张 atlas 映射 | 第一版固定单张 UV atlas；SAM 二维输出要经过 UV 投影与遮挡处理 |

静态模式还必须调整年龄数字、固定 30 岁比较、按钮和导出文件名/元数据。静态本人重建不能默认标成“30 岁”；应展示“原始重建，年龄变换不可用”。程序化演示继续保留独立、明确的演示标识。

完整路线另补充两个明确工作项：重建器的投影变换需去尺度、正交化和坐标转换，不能直接作为 `R`；年龄形变需定义源年龄及属性尺度，不能把本人形状默认锚定在 45 岁。BFM 官方存在年龄属性文件，但与当前裁剪基的对应关系必须验证，详见 [模型与数据路线核验](模型与数据路线核验.md)。

## 3. 环境与架构决定

本机只读核查：Windows，默认 Python `3.15.0`；Python Launcher 列出了 `3.15` 和 `3.14`；已找到 `uv`。GPU 为 NVIDIA GeForce RTX 5060 Laptop GPU，显存报告 `8151 MiB`，驱动 `595.79`。这些信息不证明 PyTorch、ONNX Runtime、CUDA 算子或模型已可用；本轮未做算法环境安装和推理。

拟先在独立 Python 3.11 环境验证 API 与重建依赖，实际版本以兼容性样例通过后锁定，不修改系统 Python。API 采用 FastAPI/Pydantic；第一版单 Uvicorn 进程，避免多个 Web worker 各复制一份 GPU 模型。模型由 lifespan 管理启动与释放，推理移出异步事件循环，并设置并发上限。[FastAPI lifespan 官方说明](https://fastapi.tiangolo.com/advanced/events/)

3DDFA_V2 作为重建基线候选，先验证 ONNX CPU 路径，再测试实际可用的 GPU provider。其官方仓库主要在 macOS/Linux 测试，并含本地编译步骤，因此 Windows 编译与运行是 B0 的实测项，不是既定成功结论；无需用于导出 GLB 的渲染扩展不先引入。[3DDFA_V2 官方仓库](https://github.com/cleardusk/3DDFA_V2)

SAM 是后续年龄纹理候选。官方前置环境为 Linux/macOS 与 NVIDIA CUDA，不能假定本机 Python 直接可用。先做独立环境兼容性验证；需要时采用本机 WSL2 中的独立推理进程，并保持服务入口仅供本机使用。该模块失败不应阻止基础 API、静态重建启动。[SAM 官方说明](https://github.com/yuval-alaluf/SAM#prerequisites)

第一版不用数据库、Redis、Celery 或账号系统。使用明确的适配器接口、内存元数据和有界临时资产缓存。只有实际依赖冲突或显存隔离需求得到验证后，才增加独立算法进程；不提前拆成多个微服务。

## 5. 接口冻结与最小扩展

保留当前 v1 路径和字段，不再并行扩展旧 `beta/psi` 命名：

- `GET /api/health`：保留 `models/device/version`。拟增加 `api_version` 与 `capabilities`；模型状态使用 `missing/loading/ready/error`，记录实际 backend/provider 和可读失败原因。HTTP 200 表示服务存活，不表示全部模型就绪。
- `POST /api/reconstruct`：仍接收 multipart 字段 `image`，返回 `mesh_id/shape/expr/pose/texture_url?`。拟通过契约小版本增加本次结果的 `asset_mode: static | age_morph` 和实际能力，前端解析并以结果能力为准，不能只依据全局 health。现有年龄模式继续要求全部三档目标；静态模式须明确声明，不能遇到坏 morph 就自动降级。
- `GET /api/assets/{mesh_id}/mesh.glb`：继续返回自包含静态 Mesh GLB；对应身份和表情已经应用。右手 Y-up、正面 +Z；固定一种拓扑和单张 UV。不得把局部人脸表面描述成完整头部重建。
- `POST /api/aging`：继续接收 `{mesh_id, age}`，保留现有 `shape_aged/texture_url?` 契约。当前 UI 是纹理操作：仅纹理能力可用时开放，并要求成功返回纹理；纯年龄形状随 GLB 一次性交付。后续若拆分接口，先更新契约和前端测试，不暗中改变字段语义。
- `/api/export/gltf`、`/api/export/image`：保留为后续需求；当前前端已能本地导出，不在首批实现服务端渲染或重复导出管线。

以上新增字段是**待实施的 v1.1 提案**，本轮没有修改 [api.md](api.md) 或前端代码。B1/B3 实施时同步更新 schema、前端解析、说明和浏览器测试；旧 v1 服务只按已有年龄资产路径工作，不臆测静态能力。

HTTP 状态约定：无效/损坏输入用 400 或字段校验 422；体积或像素超限 413；媒体类型不支持 415；无人脸/多人脸 422；模型未就绪 503；服务繁忙 429；内部时限耗尽 504；不存在或已清理资产 404。错误体至少含字符串 `detail`，可增加稳定 `code`；FastAPI 默认的列表型校验错误应转为前端能读的说明。

输入限制由服务端独立执行：JPEG/PNG/WebP，单文件 ≤10 MiB、≤1600 万像素；限制 multipart 总体积与字段数量，校验真实格式和解码后尺寸，不信任扩展名或 MIME。只接收 `image` 的文件内容，不提供 URL 下载入口。外部响应使用 `Cache-Control: no-store`。

默认绑定 `127.0.0.1:8000`。按实际启动方式显式配置本地页面来源，开发 `5173` 和验收 `4173` 分别列入所需白名单，禁用凭证。校验 Host 和 WS Origin；CORS 中间件不代替 WS 来源检查。[FastAPI CORS 官方说明](https://fastapi.tiangolo.com/tutorial/cors/)

## 6. 实时、缓存与资源规则

WS 客户端已固定为 JPEG 二进制、最长边 640、最多 10 FPS、单帧等待。服务端按连接维护递增 `seq`；不临时增加客户端未实现的二进制头。每个接收帧产生且只产生一条终结消息 `face_state` 或 `error`，`status` 不能作为确认。`NO_FACE/MULTI_FACE` 是可继续处理的单帧错误，其余严重错误明确结束连接。

`bbox` 使用 `[x,y,width,height]`，5 点坐标对应收到的 JPEG，点位为左眼、右眼、鼻尖、左嘴角、右嘴角；B0/B6 用标注示意固定“左右”的定义并验证镜像。所有服务端文本消息以 UTF-8 实际编码验证 ≤1024 字节，控制小数精度，不重复发送整组 shape/expr。不把裁剪坐标误当原图坐标。

内部单帧 deadline 应小于前端 8 秒等待上限；HTTP 内部预算应为前端 30 秒总等待保留响应时间。先测量模型耗时再定默认值。必要时再设计异步任务协议，不在现有接口里静默等待数分钟。一次性纹理慢任务不得占住事件循环或无限拖延实时队列。

缓存建议默认 TTL 30 分钟、磁盘派生资产上限 512 MiB、原图/对齐裁剪只在有界内存中短暂保留，具体限额在 B7 压测后调整。使用随机不可预测的 `mesh_id`；限制访问到已登记的单一缓存根目录，拒绝路径穿越。写入先用临时文件，成功后发布；清理跳过正在读取的资产，服务重启清理遗留临时文件。

用户取消后停止等待、丢弃迟到结果并清理任务产物；不能承诺已经进入 GPU 的算子立即停止。关闭连接释放对应帧与任务引用，长期运行有界；失败和显存不足不得回传演示成功或自动上传云端。日志仅记录请求 ID、阶段、耗时、错误码和资源摘要，不记录照片、摄像头帧、完整形状参数或原始文件名。
