## 1. 这次要核对什么

另一成员从一台全新 Windows 机器开始：

1. 只按锁文件安装 Python 依赖和 npm 依赖。
2. 按 [模型资产台账](model-assets.md) 自行取得获准模型。许可未收口的登记保持 unresolved。
3. 断开网络后，用 `tools/local-run` 启动开发模式和 `--production`。
4. 记录版本、锁文件哈希、模型文件是否存在及其哈希、健康检查，以及和本文的偏差。
5. 由执行人自己填写通过或未通过。准备者不代填。

只读检查 `tools/repro_check.py` 可以在安装完成之后帮执行人核对第 3 步以前的环境和一次启动烟雾。它不安装软件，不改清单，也不把缺模型写成已有文件。

## 2. 锁文件里的版本

不要把某一台机器上的补丁号写成新的要求。下面只转述仓库锁文件。

| 项目 | 锁文件怎么写 | 说明 |
|---|---|---|
| Python | `backend/uv.lock` 的 `requires-python = "==3.11.*"` | 任意 3.11 补丁都可以。锁文件没有指定 3.11.16 或 3.11.18 |
| Node | `frontend/package-lock.json` 根包 `engines.node` 为 `>=22.18.0` | 满足该范围即可。锁文件没有把 22.23 或 24.14 写成唯一版本 |
| uv | 不在 `uv.lock` 里 | 用官方安装方式获得 uv，再执行 `uv sync --locked`。检查脚本只记录本机 `uv --version` |
| npm | 使用随 Node 提供的 npm，命令只用 `npm ci` | 不要用 `npm install` 重新解析版本 |

`uv sync --locked --extra inference` 会安装的直接依赖，版本以 `backend/uv.lock` 为准：

| 用途 | 包 | 锁内版本 |
|---|---|---|
| 服务 | fastapi | 0.146.0 |
| 服务 | pillow | 13.0.0 |
| 服务 | pydantic | 2.14.1 |
| 服务 | python-multipart | 0.0.32 |
| 服务 | uvicorn（extra standard） | 0.54.0 |
| 推理 extra | numpy | 2.4.6 |
| 推理 extra | onnxruntime | 1.31.0 |
| 推理 extra | opencv-python-headless | 4.14.0.94 |
| 开发组 | httpx | 0.28.1 |
| 开发组 | pytest | 9.1.1 |
| 开发组 | pytest-asyncio | 1.4.0 |
| 开发组 | ruff | 0.17.1 |

前端直接依赖以 `frontend/package.json` 和 `package-lock.json` 为准：three 0.186.1，vite 8.3.4，typescript 7.0.2，@types/three 0.186.0，@playwright/test 1.64.1。`npm ci` 还会安装锁文件里的传递依赖。平台不适用的可选二进制包可以不出现，检查脚本按当前操作系统过滤。

Windows 上 uv 会安装带 `sys_platform == 'win32'` 标记的 colorama，并且不会要求 uvloop。Linux 相反。这是锁文件里的环境标记，不是两套依赖。

## 3. 全新 Windows 上的安装

路径含空格时保留引号。下面的目录只是示例，换成实际克隆位置。

先安装 Python 3.11（64 位）、满足 `>=22.18.0` 的 Node.js，以及 [uv](https://docs.astral.sh/uv/)。这三样是安装器，锁文件不管 uv 自己的版本。然后克隆仓库，检出包含本说明的提交。

联网只用于这一次安装：

```powershell
Set-Location -LiteralPath 'D:\project file\AgeMorph3D'
uv --cache-dir output\uv-cache sync --project backend --locked --extra inference --python 3.11
Set-Location -LiteralPath 'D:\project file\AgeMorph3D\frontend'
npm ci
Set-Location -LiteralPath 'D:\project file\AgeMorph3D'
backend\.venv\Scripts\python.exe --version
node --version
uv --version
```

`uv sync --locked` 拒绝锁文件以外的版本。`--extra inference` 是服务在许可通过之后加载 ONNX 所需要的额外依赖；不加它时，无模型的 API 仍能启动，但检查脚本会把推理包记为缺失。不要执行 `pip install`，不要改 `uv.lock` 或 `package-lock.json`。

缓存目录 `output\uv-cache` 已被 Git 忽略。虚拟环境和 `node_modules` 也在忽略规则里，不要提交。

## 4. 按台账取得模型

权重不在源码仓库里。本说明不附带文件，也不另写一份哈希，避免和台账漂移。执行人自己阅读并遵守这些材料：

- [模型资产台账](model-assets.md)：每项资产的来源、许可和还缺的证据。
- `backend/model-manifests/yolov5n05-face.research.json` 与 `backend/model-manifests/3ddfa-v2.research.json`：服务使用的检测、回归、BFM 和参数统计元数据。它们不是权重。
- [B0 模型验证与复现](B0模型验证与复现.md)：已获准文件如何放到 `data/models/`，以及研究清单怎样和权重放在同一目录。
- [模型资产诊断与严格服务缺项](模型资产诊断与严格服务缺项记录.md)：文件完整仍然可以是 unresolved，诊断不授予 ready。

取得前先满足台账里的许可条件。BFM 有单独的非商业研究授权，不能自动覆盖 YOLO 权重或修改后的派生文件。两份研究清单的 `license_status` 仍是 unresolved。不要改成 verified，不要为了让健康检查变成 ready 而编辑清单。启动器拒绝 `--research-allow-unresolved`。

SAM 与 FG-NET 的来源和限制在 [年龄模型与校准样例获取记录](年龄模型与校准样例获取记录.md)。它们不打开服务的年龄能力。这次启动复现不把 SAM 环境当成通过条件。

放好文件之后，把清单路径传给检查脚本。脚本只读取清单里相对路径点名的文件：算出大小和 SHA-256，和清单对比。文件不在就记 `missing`，`observed_sha256` 为 null。它不会创建占位文件。

## 5. 断网后的启动

安装和模型文件都到位之后，断开网络或禁用适配器，再启动。开发模式和 `--production` 都要做。Node 不在默认 PATH 上时，先设置 `AGEMORPH_NODE`，例如本机曾经使用的 `D:\JAVA run tools\node.exe`。

```powershell
Set-Location -LiteralPath 'D:\project file\AgeMorph3D'
$env:AGEMORPH_NODE = 'D:\JAVA run tools\node.exe'
.\tools\repro-check.ps1 --smoke-mode dev
.\tools\repro-check.ps1 --smoke-mode production
.\tools\repro-check.ps1 --smoke-mode dev `
  --detector-manifest 'data\models\yolov5n05-face\manifest.json' `
  --reconstructor-manifest 'data\models\3ddfa-v2\manifest.json'
```

检查脚本会调用现有的 `tools/local_run.py`，顺序是 start、读取 `http://127.0.0.1:8000/api/health`、stop。开发前端是 `127.0.0.1:5173`，生产前端是 `127.0.0.1:4173`。报告写到被忽略的 `output/repro-check/report.json`。也可以直接看启动器：

```powershell
.\tools\local-run.ps1 start
Invoke-RestMethod 'http://127.0.0.1:8000/api/health' | ConvertTo-Json -Depth 6
.\tools\local-run.ps1 stop
.\tools\local-run.ps1 start --production
Invoke-RestMethod 'http://127.0.0.1:8000/api/health' | ConvertTo-Json -Depth 6
.\tools\local-run.ps1 stop
```

检查脚本不调用 `/api/aging`。现有服务契约里，年龄接口在模型未就绪时返回 503 `MODEL_NOT_READY`。执行人如果要看这一项，用启动器文档里的请求，并把实际状态码写进记录。

端口已被其他程序占用时，脚本退出 3，不结束那个未知进程。停止后若 8000 或本次前端端口仍接受连接，退出 5。

## 6. 健康检查的两种结果

无清单时，四个模型都是 `missing`，四项能力都是 false。准备机看到的检测和重建 detail 是「尚未配置已核验的模型清单。」年龄形状和年龄纹理分别是「尚未接入可追溯且经过校准的年龄形状资产。」和「尚未接入经过校准和验证的年龄纹理模型。」`device` 为 `cpu`，`api_version` 为 `1.2`，`version` 为 `0.1.0`。HTTP 200 只表示进程可达。

清单文件存在、但 `license_status` 仍是 unresolved 时，检测和重建变为 `error`，detail 为「模型权重许可尚未完成核验。」年龄两项仍是 missing，四项能力仍是 false。这是服务在读权重之前就停住的许可门槛。文件是否真的在磁盘上，要看检查脚本的 `models` 段，不要从这条 error 推断文件已经匹配。

清单路径指向一个不存在的文件时，源码会把该角色记为 `missing`，detail 为「配置的模型清单文件不存在。」准备机没有单独再跑这条路径。

任何一种结果都不是 ready，也不是 L02 通过。

## 7. 检查脚本的边界

`tools/repro_check.py` 和 `tools/repro-check.ps1` 只做这些事：

- 比较虚拟环境里的 Python 包和 `uv.lock`，包括开发组和 `inference` extra，并遵守平台标记。
- 比较 `node_modules` 和 `package-lock.json` 里适用于本机的包。
- 计算两份锁文件的 SHA-256，并确认锁内记录了 sha256 或 npm integrity。
- 在传入清单时，核对该清单点名的文件。不传入就明确写未配置。
- 读取 `git rev-parse HEAD` 和工作区是否干净。
- 用现有启动器做上述烟雾。子进程设置离线环境变量，健康检查只访问 `127.0.0.1`。

Linux 上它会尝试 `unshare(CLONE_NEWNET)`。没有权限时记录 `not_applied`，不使用 sudo，也不改系统配置，然后继续只访问回环地址，并核对服务进程自己的套接字。Windows 没有这个调用，报告写 `not_applicable`。

退出码 0 表示这次检查没有发现版本、锁、烟雾或已配置文件的失败。模型未配置、uv 版本不在锁里、工作区不干净，记在 `gaps`，不把退出码变成 0 的反面含义。`l02_executed` 和 `l02_signed_off` 固定为 false，`conclusion` 固定为 `preparation_check_only`。没有参数可以把它们改成通过。

| 退出码 | 含义 |
|---|---|
| 0 | 检查跑完。不是 L02 通过 |
| 1 | 版本或已配置模型文件不一致，或清单点名的文件缺失 |
| 2 | 没有虚拟环境、Node 或 `node_modules`。脚本不会去安装 |
| 3 | 端口已被占用，未知进程保持不动 |
| 5 | 停止后端口仍接受连接 |
| 6 | 报告路径不在项目内被忽略的 `output/` 或 `logs/` |

成员 B 可以在自己的 Windows 上先做一次演练，确认脚本和启动器能打开。那次演练仍然不是 L02。L02 要另一名成员在自己的干净环境里做，并填写下一节。

## 9. 准备机上的核对

这是 Linux 准备环境，不是另一成员的 Windows，更不是 L02 完成记录。

解释器是项目虚拟环境 Python 3.11.18，Node v22.23.4，uv 0.13.6。3.11.18 只是当天 `uv python install 3.11` 解析到的补丁。uv 0.13.6 只是准备机安装器的版本。二者都不是锁文件要求。当时 `backend/uv.lock` 的 SHA-256 是 `6433d7ba47036e2596d6e2f83e8937607f4b9a331ab9d63445ead653a32039d3`，`frontend/package-lock.json` 的 SHA-256 是 `9ef259b8f8a55cd04cc2d8c79c893950eba4b9dd7d59c5f26b7d38f461130451`。38 个适用 Python 包和 28 个适用 npm 包与锁一致。`pytest -q backend/tests/test_repro_check.py` 为 13 项通过。项目 Ruff 检查和格式检查通过。没有改 API 或前端源码，没有重跑既有的 2956 项后端或 340 项前端。

同一脚本接着做了启动烟雾。无清单时 `--smoke-mode both` 退出码 0：开发模式健康为 missing、能力全 false，停止后 8000 和 5173 不再接受连接；生产模式同样是 missing，前端端口是 4173，停止后也不再接受连接。`frontend/dist/index.html` 由启动器的已安装依赖构建产生。服务进程没有持有回环以外的套接字。`l02_executed` 为 false。

把两份研究清单传给同一脚本时，退出码 1。健康里检测和重建都是 error，detail 为「模型权重许可尚未完成核验。」，能力全 false。四个清单点名的权重在清单目录旁不存在，报告为 `missing`，`observed_sha256` 为 null。两份清单文件的字节在检查前后没有变化。这个退出码 1 是缺文件，不是脚本崩溃，也不是把 unresolved 收成 ready。

无特权时网络命名空间返回 EPERM，报告 `not_applied`。用 root 单独调用同一隔离函数时，命名空间可以建立，连到 `1.1.1.1:443` 失败（errno 101），回环地址可以绑定。复现脚本不会因此要求 sudo。

这次检查时的 git commit 是 `4372c40350f97b5d1afc724a83b1b08b6681b7d7`，工作区有未跟踪的准备文件，所以报告里 `dirty` 为 true。那是提交这些文件之前的状态。正式执行必须记录执行当时的 commit，不能把这次准备机的 dirty 结果抄成通过。
